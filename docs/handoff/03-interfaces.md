# Interfaces

Everything FTUSA needs to integrate with Fair Exchange: the record schema, the data-tool contracts,
the agent's request/action/event schemas, and the API routes with their roles.

## Record schema

The record is the single stored output of a conversation. It is generated from the Pydantic models in
`agent/src/fex/models.py`; never hand-edit the generated files.

- JSON Schema: [`agent/schema/conversation-record.schema.json`](../../agent/schema/conversation-record.schema.json)
  (and the API copy, [`api/src/types/conversation-record.schema.json`](../../api/src/types/conversation-record.schema.json)).
- TypeScript types: [`api/src/types/conversation-record.ts`](../../api/src/types/conversation-record.ts).
- Contract and field meanings: [#26](../specs/26-write-back.md). A record is `completed` (with a stored
  consent scope) or `declined` (identifiers, status and time only — no narrative). The schema enforces
  that a declined record carries no narrative content.
- Regenerate with `agent/scripts/generate_types.py`; a CI drift test fails if the generated files and
  the models disagree.

## Data tools

The full input/output/guarantee contract for every data tool is in [tool contracts](tool-contracts.md):

- the **scope rule** (producer only from the session, no producer/location/crop parameter on any tool);
- **step gating** (tools run only in `respond`, after the producer confirms the playback);
- **citations** (how a tool result feeds the verifier);
- each tool: `get_producer_record` ([#14](../specs/14-producer-record-tool.md)),
  `get_regional_context` ([#15](../specs/15-regional-context-tool.md)),
  `find_peer_examples` ([#16](../specs/16-peer-example-tool.md)), and standards grounding
  ([#17](../specs/17-standards-grounding.md));
- the shipped data files and how to rebuild them.

## Agent request, action and event schemas

The chat API invokes the AgentCore Runtime with one request per call. The requests, actions and events
are Pydantic models in the agent package, with JSON Schema and TypeScript generated from them (same
discipline as the record schema). The shared contract is owned in [#13](../specs/13-conversation-steps.md):

- **Requests** carry `producerId` and `conversationId` (set by the API from the identity, never the
  client) plus `kind`: `start`, `message` (`text`), `action` (`{ name, args }`), `resume`,
  `auto_close` (`reason`).
- **Actions**: `confirm_playback`, `correct_playback`, `reopen_playback`, `retry_answer`,
  `set_consent`, `set_feedback`, `end` — each valid in specific steps (table in #13).
- **Events**: `text`, `claim`, `answer`, `step`, `actions`, `record_saved`, `error`, `done`.
- **Resume** returns `step`, `language`, `allowed`, the latest `answer`, and `history`.

Wire format between the API and the runtime: the AgentCore SDK streams a generator entrypoint as
Server-Sent Events (`data: <json>` lines) and returns `resume` as plain JSON; `api/src/core/agent.ts`
reads both. Shared fixtures in `api/src/core/fixtures/` are generated by `agent/tests/test_wire_format.py`
([#89](../specs/25-chat-endpoint.md)).

## API routes and roles

One REST API (TypeScript, Node.js). Identity comes from the one resolver ([#11](../specs/11-identity.md));
no handler reads a producer ID from the request. A missing identity is 401; a missing role is 403.

| Route | Role | Streams | Spec |
|---|---|---|---|
| `GET /me` | any identified | no | [#11](../specs/11-identity.md) |
| `POST /conversations` | producer | yes | [#25](../specs/25-chat-endpoint.md) |
| `POST /conversations/{id}/messages` | producer | yes | [#25](../specs/25-chat-endpoint.md) |
| `POST /conversations/{id}/actions` | producer | yes | [#25](../specs/25-chat-endpoint.md) |
| `GET /conversations/{id}` | producer | no | [#25](../specs/25-chat-endpoint.md) |
| `GET /conversations` | producer | no | [#25](../specs/25-chat-endpoint.md) |
| `GET /me/records` | producer | no | [#32](../specs/32-your-record.md) |
| `GET /records`, `GET /records/{id}`, `PATCH /records/{id}`, `POST /records/{id}/approve` | reviewer | no | [#27](../specs/27-review-api.md) |
| analytics routes | admin | no | [#29](../specs/29-analytics-api.md) |

Chat streams to the web client are `application/x-ndjson`. Common errors: 400 (unknown field, or a
producer/conversation ID in the body), 401 (not identified), 403 (wrong role), 404 (missing or
someone else's record — same response, so ownership never leaks), 409 (closed, or a turn in progress).
Each streaming turn holds a turn lock so a 409 is a real HTTP 409; agent calls are cut off at 290 s
(Lambda 300 s, lease 330 s); resume calls at 20 s so a stalled agent is skipped, not blocking the sweep.

Code: `api/src/core/`, `api/src/handlers/` (`conversations.ts`, `sweep.ts`, `review.ts`, `me.ts`,
`analytics.ts`, `writeBack.ts`). Agent: `agent/src/fex/conversation/`.

## Agent runtime permissions

The runtime execution role gets only what the agent needs; the shared contract is owned in
[#13](../specs/13-conversation-steps.md) ("Agent runtime permissions"): DynamoDB on the records table,
the AgentCore Memory resource ([memory](../specs/memory.md)), `bedrock:InvokeModel` /
`InvokeModelWithResponseStream` on the configured `us.` profiles, `bedrock:ApplyGuardrail` on the FEX
Guardrail ([#12](../specs/12-guardrail.md)), `bedrock:Retrieve` on the standards Knowledge Base
([#17](../specs/17-standards-grounding.md)), `comprehend:DetectPiiEntities`
([#20](../specs/20-pii-flagging.md)), and S3 read on the producer and peer data objects
([#14](../specs/14-producer-record-tool.md)).
